# Documentation advocacy and culture

Docs fail more often for organisational reasons than for writing reasons. This skill
helps people win support for docs, build systems colleagues will actually use, and
work confidently with technical experts.

## Pick the situation

| Situation | Go to |
|---|---|
| "My deadlines barely allow tests. How do I justify docs?" | [references/building-mindshare.md](references/building-mindshare.md) (make the case) |
| "Our internal docs are a mess. How do I fix the culture?" | [references/building-mindshare.md](references/building-mindshare.md) (rollout plan) |
| "I'm in support, or a writer working with support." | [references/support-teams.md](references/support-teams.md) |
| "I'm 'just' a writer and engineers don't take docs seriously." | [references/imposter-syndrome.md](references/imposter-syndrome.md) |

## Deliverables this skill can produce
1. **A one-page business case** for docs. Cover the problem (a concrete, small, winnable
   scope), its current cost (onboarding time, repeated support tickets, lost adoption),
   the proposal, the effort, and how success will be measured.
2. **A rollout plan** for an internal docs system: scope, stakeholders to invite, the
   taxonomy ("where do I put it?"), templates, a meeting cadence, and long-term ownership.
3. **A support–docs workflow:** an intake channel for doc issues, a review loop with
   support agents, and metrics such as fewer repeat tickets.
4. **Talking points or a coaching note** for a writer facing scepticism or knowledge gaps.

## Principles to apply
- **Start small and winnable.** "Internal project docs in Engineering" beats "fix
  company communication".
- **Make it easy.** Templates should produce a doc outline in seconds, with the same
  hierarchy in every project.
- **Make it public and participatory.** Invite every team, even if they don't attend.
- **Make it long-term.** A docs system needs ongoing care. Treated as a one-off tooling
  project, it fails like the last one did.
- **Docs are part of the product.** Push for documentation in the team's Definition of Done.

Keep advice grounded in the user's context, and ask about team size, tools, and
constraints before producing a plan. Don't invent metrics. Mark estimates as estimates.
